# Спека: чужие локальные агенты в клиенте Volt (видимость, удаление, утечка)

Статус: прошла ревью (свежий агент, по коду master `4d800880c`), код не менялся. Ждет решения владельца. 2026-10-07.

## Симптом

На пилоте агенты, добавленные по коду до входа через Keycloak (анонимная сессия),
после входа остались в списке, но у них пропало меню «удалить». Любой, кто войдет
в клиент на этом устройстве, их видит.

## Факты (по коду master `4d800880c`)

1. Список агентов не фильтруется по владельцу: `getAllAgents` в `src/dal/agents.ts:61`
   отдает все строки `agents` с `deletedAt IS NULL`. Хук `useAgents` и страница
   настроек показывают все, что лежит в локальной базе.
2. Строка агента несет `userId` пользователя, под которым ее создали
   (`create-agent-detail-panel.tsx:53`, `userId: currentUserId`). Единственный путь
   создания — эта панель; кнопка недоступна без сессии.
3. Управление (меню «⋯» с удалением и правкой) открыто только владельцу:
   `agent-detail.tsx:102`, `isEditable = flavor === 'custom' && canManageForkCustomAgent(agent.userId, currentUserId, isAnonymous)`.
   Форк-хелпер `src/fork/agents/manage-anonymous-agent.ts` снимает проверку владельца
   только для анонимной сессии. Под SSO проверка строгая, поэтому сироты нельзя удалить.
4. Токены агентов (bearer от сопряжения) лежат в локальной таблице `agents_secrets`
   с ключом только `agentId`, без `userId` (`src/db/tables.ts:347`). Таблица не
   синхронизируется. Кто видит строку агента, тот и использует его токен:
   транспорт берет агента по id.
5. Синхронизация: правила PowerSync отдают клиенту только строки `user_id =
   bucket.user_id` (`backend/conf/powersync/config.yaml:44`). Загрузка на сервер
   всегда переписывает `user_id` на пользователя сессии и не трогает чужие строки
   (`backend/src/dal/powersync.ts:90-190`). Анонимные сессии на сервер не пишут
   (`403 ANONYMOUS_SYNC_FORBIDDEN`).
6. Смена пользователя локальную базу не чистит. Чистка только по выбору «Удалить
   данные с устройства» при выходе (`logout-modal.tsx`, `clearLocalData`); по
   умолчанию «оставить». Отдельного «сменился user.id, убрать чужое» нет
   (`use-app-initialization.ts` такого не делает).
7. Комплект собран с `VITE_AUTH_MODE=sso`, `VITE_AUTH_ENABLE_ANONYMOUS=false`, бэкенд
   `AUTH_ALLOW_ANONYMOUS` не задан (false). Значит в поставочном клиенте анонимную
   сессию получить нельзя; сироты на машине пилота пришли из более ранних сборок или
   со стенда разработки (локальная база переживает обновление клиента).

## Угроза

На общем устройстве второй пользователь после входа видит агентов первого (строки
остались локально, «оставить данные» при выходе) и может ими пользоваться через
локальный токен сопряжения. Это доступ к агенту voltd под чужим принципалом. Удалить
их он не может (п. 3), поэтому они вечные. То же для анонимных сирот.

## Варианты

### A. Видимость и использование только своих строк, чужие чистятся при смене пользователя

- `getAllAgents`/`useAgents` и выбор агента в чате получают `currentUserId` и
  отдают только `userId = currentUserId` (плюс built-in и system). Без сессии —
  только built-in/system.
- Транспорт ACP при подключении проверяет владельца строки; чужую не открывает,
  токен из `agents_secrets` для чужой строки не читает.
- При инициализации приложения: если `session.user.id` не равен сохраненному
  `lastUserId` (локальная настройка), удалить локально чужие строки `agents` и их
  `agents_secrets`, затем записать новый `lastUserId`. Анонимные сироты тем самым
  исчезают при первом входе через SSO.
- Проверка владельца в `agent-detail` остается строгой; форк-послабление для
  анонимных не нужно (анонимных нет) — убрать вместе с его тестом.
- Итог для пользователя: все, что он добавил сам после входа, видно и удаляется;
  чужое и анонимное не видно и не живет на диске.

### B. Усыновление сирот при первом входе

Переписать `userId` сирот на вошедшего. Удобно, но на общем устройстве усыновляет
чужих агентов вместе с их токенами сопряжения, то есть закрепляет утечку. Не брать.

### C. Ничего не менять

Утечка и вечные сироты остаются. Не брать.

## Рекомендация

A. Малый объем: фильтр в DAL (две функции), одна проверка в транспорте, одна
процедура чистки при смене пользователя, тесты на каждое. Усыновления нет.

## Решения владельца продукта (2026-10-07)

1. Общие устройства в пилоте возможны: вход разных пользователей на одном устройстве
   есть в сценариях. Вариант A нужен по существу.
2. Перенос анонимных агентов при первом входе не нужен.
3. Сироты сейчас есть только на машине разработки, где агентов настраивали без
   входа; на машинах пилота поставочная сборка анонимной сессии не дает.

## Что проверить на ревью

- Все места, где строка агента берется по id без владельца (чат, транспорты, deep
  link на агента, палитра Cmd+K, восстановление последнего агента в чате).
- Таблица `agents_secrets`: остаются ли сиротские токены после чистки.
- Поведение при `session` еще не загружена (`currentUserId = null`): список пустой,
  но не чистка.
- Выход с «оставить данные» и повторный вход того же пользователя: ничего не теряется.

- п.2: без сессии кнопка недоступна только на странице настроек; быстрое создание из
  шапки (`header.tsx:222`, `useCreateItem`) гейтится по capability, не по сессии.
- п.5: путь правил синка в репо `deploy/config/powersync-config.yaml:35` (в комплекте
  `backend/conf/powersync/config.yaml:44`). Серверная перезапись `user_id`:
  `backend/src/dal/powersync.ts:132` (PUT), скоуп по владельцу в PATCH/DELETE `:178`, `:190`.

## Ревью: очередь загрузки

- `agents` синхронизируется, локальное удаление через drizzle попадет в `ps_crud` и
  уедет на сервер. DELETE чужой строки сервер скоупит по владельцу, вернет `false`,
  роут ответит 400 (`api/powersync.ts:280-282`), коннектор не завершит транзакцию
  (`connector.ts:194-199`) и очередь встанет навсегда, блокируя все дальнейшие
  загрузки. Это главный риск чистки, не потеря данных.
- Если в очереди еще лежит PUT сироты, батч создаст ее заново под вошедшим.
- Свои строки после локального удаления бакетом восстановятся, чужие нет.
- Чистку делать не через синк-вью: удалить и в той же транзакции подчистить `ps_crud`
  (прецедент `src/db/powersync/database.ts:464-474`), либо строго в окне после
  `onSignInSuccess` и до `connectToSync` (`database.ts:241`). `agents_secrets`
  локальная, ее удаление в очередь не попадает.

## Ревью: дополнительные векторы

- `chat-store.ts:308` пишет `selected_agent` в синхронизируемые `settings`, и
  `chat_threads.agentId` тоже синк: чужой id уезжает на сервер под вошедшим и
  приезжает на другие устройства; гидрация его восстанавливает. Чистка обязана занулять оба.
- iroh: клиентский секрет один на устройство (`cleanup.ts:83-85`), не на пользователя.
- `canManageForkCustomAgent` при анонимной сессии отдает управление любой строкой,
  включая строку прошлого SSO-пользователя (на стендовых сборках рабочий вектор).

## Решение ревью: A с поправками, четыре шага, каждый отдельно

1. Фильтр владельца в двух точках чтения: `agents.ts:61` и
   `use-hydrate-chat-store.ts:200`. Через них идут шапка, канвас, настройки, палитра и
   восстановление в чате. Без сессии список пустой, чистки нет.
2. `userId` в `WHERE` у `updateAgent`/`deleteAgent`; резолв токена в `connect.ts`
   через строку с предикатом владельца, а не `getAgentSecrets(agentId)`. После этого
   утечка не эксплуатируется.
3. Чистка при смене пользователя (отдельный PR, единственный шаг, который может
   сломать синк): `lastUserId` в `local-settings-store` (не синк); запуск сразу после
   `onSignInSuccess`, до `connectToSync`; удалить чужие `agents` + `agents_secrets`,
   в той же транзакции `DELETE FROM ps_crud` для них; занулить `settings.selected_agent`
   и `chat_threads.agentId` с удаленными id. При `currentUserId === null` не запускать.
4. Снять `canManageForkCustomAgent` с его тестом, последним и только если анонимные
   сборки точно не поставляются.
