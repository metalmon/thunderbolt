# Адрес сервера и сборки под разных заказчиков

Один двоичный файл не может нести адрес всех заказчиков сразу, а запечённый адрес
одного — это адрес, с которым он уедет ко всем остальным. Поэтому адрес задаётся
**на сборку**, а не на репозиторий.

## Что решает адрес

`src/stores/local-settings-store.ts`:

```ts
cloudUrl:      import.meta.env.VITE_THUNDERBOLT_CLOUD_URL || 'http://localhost:8000/v1',
operationMode: import.meta.env.VITE_THUNDERBOLT_CLOUD_URL ? 'server' : 'local',
```

Переменная задана при сборке — серверный режим с этим адресом. **Пусто — автономный
режим.** Запасной `localhost` в первой строке к режиму отношения не имеет: он
подставляется, чтобы поле не осталось пустым, и в автономном режиме не используется.

Автономная установка **не спрашивает вход**: `use-auth-gate.ts` возвращает `allowed`
раньше, чем доходит до ветки SSO. Адрес вводит оператор потом, в настройках
(`src/fork/local-mode/server-section.tsx`, затвор `VITE_VOLT_ALLOW_SERVER_EDIT`), и с
этого момента режим входа решает `/config` развёртывания.

⚠ `VITE_AUTH_MODE=sso` в `.env.production` остаётся намеренно. Это **запасное**
значение, которым клиент пользуется, пока `/config` не ответил. Пока адреса нет, оно
ничего не делает; как только адрес введён — вступает в силу. Хранить его в сборке
дёшево, в отличие от адреса: имя режима входа одинаково у всех, имя узла — нет.

## Сборка в CI

| Что собираем | Откуда берётся адрес |
| --- | --- |
| Клиент (`build-all.yml`) | параметр запуска **`backend_url`**, по умолчанию пусто |
| CLI (`cli-release.yml`) | переменная репозитория **`VOLT_CLI_CLOUD_URL`** |

**Обычная сборка и сборка по метке — автономные.** На событии `push` параметров нет,
и `inputs.backend_url` разворачивается в пустую строку. Это и есть нужное умолчание,
а не случайность.

Сборка под заказчика с адресом:

```sh
gh workflow run build-all.yml -R metalmon/thunderbolt --ref v0.1.152 \
  -f backend_url=https://backend.example.ru/v1
```

⚠ **Переменной репозитория `VITE_THUNDERBOLT_CLOUD_URL` больше нет** — её читали четыре
рабочих последовательности сразу, то есть у ошибки «ушло не тому заказчику» было четыре
двери. Удалена 10.11.2026. Если какая-то последовательность её ещё называет (в том числе
выключенные), она развернётся в пустую строку — то есть в автономный режим. Это
безопасная сторона отказа, и ломать её переизобретением переменной не надо.

У CLI автономного режима нет, адрес ему обязателен — отсюда отдельная переменная и
явный отказ сборки, если она пуста.

## Сборка на своей машине

Vite читает файлы окружения по возрастанию приоритета:

```
.env  →  .env.local  →  .env.production  →  .env.production.local
```

⚠⚠ **`*.local` сильнее всего и в git не хранится.** На машине разработчика там обычно
лежит свой адрес, и поэтому локальная сборка **не воспроизводит то, что уедет
заказчику**: получится серверный режим, даже когда в `.env.production` адреса нет. На
этом легко обмануться — именно так и вышло при вводе этой схемы.

Собрать так, как соберёт CI:

```sh
VITE_THUNDERBOLT_CLOUD_URL= bun run build        # пустая строка перебивает все файлы
```

## Как проверить готовый пакет

Не на слово, а по собранному:

```sh
# адреса заказчика быть не должно
grep -rl 'backend\.example\.ru' dist/assets/*.js

# умолчание режима
grep -ro "cloudUrl:[^,]*,operationMode:[^,]*" dist/assets/*.js | head -1
```

Ожидается `operationMode:\`local\`` для автономной сборки и `\`server\`` для сборки с
адресом. Это ровно та проверка, которой ловится перепутанный файл окружения.

Смежно: [автономный режим](autonomous-mode.md), [сборка форка](fork-assembly.md).
